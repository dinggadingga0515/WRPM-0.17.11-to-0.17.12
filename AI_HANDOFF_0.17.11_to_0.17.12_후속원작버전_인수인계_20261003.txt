━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[C1. 고속 Full Read transport]
목표:
대용량 Crack RP 전체읽기를 빠르게 하면서 중간 네트워크 오류 때문에 전체 작업이 끊기지 않게 한다.

기준 상수(새 upstream 사정에 따라 조정 가능하지만 약화하려면 근거 필요):
- fastPageSize = 300
- legacyPageSize = 50
- retryCount = 5
- retryBaseDelayMs = 1200
- retryMaxDelayMs = 12000
- recoveryRounds = 2
- recoveryCooldownMs = 8000
- fallbackCooldownMs = 1200
- requestTimeoutMs = 60000
- pageDelayMs = 100
- maxMessages = 1,000,000
- maxPages = 20,000

필수 동작:
- 300/page 우선.
- 어느 cursor에서든 300 모드가 복구 불가능하게 실패하면 “같은 cursor”에서 50/page로 fallback.
- 첫 페이지에서만 fallback하는 구현은 불합격.
- 401/403은 즉시 인증 오류.
- 408/425/429/5xx/네트워크는 transient로 재시도.
- Retry-After가 있으면 반영.
- 영구 오류는 bounded retry 이후 명시적으로 실패.
- maxMessages/maxPages 도달은 truncation 성공이 아니라 명시적 실패.

절대로 잃으면 안 되는 Manager 검사:
- cursor 반복 탐지.
- 빈 page + next cursor 탐지.
- message ID dedupe.
- 동일 message ID의 내용/signature 변경 탐지.
- 조회 중 room/branch 변경 stale.
- 페이지 경계 turn carry.
- buildCompletedAiDialogueTurns와 동등한 완료 USER+AI 턴 판정.
- 단일 미완성 carry 2,000,000자 안전선(새 upstream이 더 엄격한 경우 upstream 유지).

[C2. Full Read single-flight]
- 동일 chatId의 동시 “전체 history” 호출은 물리 read 하나를 공유.
- subscriber별 Promise/취소 상태 분리.
- 한 subscriber 취소가 다른 subscriber를 죽이면 안 됨.
- 모든 subscriber 취소 시에만 physical abort 가능.
- aborting flight는 새 caller가 join하지 않게 map에서 분리.

[C3. Cache-first + finalFresh]
기준:
- cache TTL 120초.
- 최근 약 50 messages frontier signature로 최신성 확인.
- <=12MiB deep snapshot.
- 12~36MiB shallow snapshot.
- >36MiB full-history cache 비활성.
- message mutation 성공 시 해당 chatId hard invalidation/revision 증가.
- append/reroll/generation 변화는 frontier mismatch로 cache 폐기.

finalFresh 계약:
- 최종 저장/적용의 source 판정은 cache를 신뢰하지 않는다.
- finalFresh=true는 새 physical read를 수행한다.
- 최종 판정에 오래된 shared flight를 재사용하지 않는다.

0.17.12에서 finalFresh를 요구한 역할:
1. 수동 전체 구축 source 확인.
2. 통합 이어갱신 source 확인.
3. 복구 job source 확인.
4. full/custom 수동 업데이트 source 확인.
5. 전체 기억 재구축 파일 생성 source.
6. 전체 기억 재구축 결과 적용 전 source 재검증.

새 upstream에서 역할이 통합/분리됐으면 동등한 최종 검증 지점에 적용한다.

[C4. 안전한 취소]
- 읽기/분석 준비 단계: 취소 가능.
- DB mutation/save/commit 시작 이후: 중간 취소 금지.
- commitStarted 같은 경계가 있어야 함.
- 취소는 USER_CANCEL과 network/error를 진단상 구분.

[C5. RP 원문 내보내기]
- 전체 원문 내보내기는 finalFresh read.
- 실제 read control과 “읽기 중단” UI 연결.
- 진행상태에 messages/pages/mode 표시.
- 정상 완료 전 다운로드 버튼 활성화 금지.
- 원문 내보내기로 DB 기억/체크포인트가 변경되면 불합격.

[C6. 전체 재구축 다운로드]
- 다중 PART를 browser에 동시 자동 클릭하지 않는다.
- PART 2개 이상이면 ZIP 1개를 권장 경로로 제공.
- STORE ZIP / UTF-8 filename / CRC32.
- 개별 TXT 재다운로드 유지.
- TXT 순차 다운로드 fallback 유지.
- ZIP 생성 중 취소 가능.
- 닫기/완료 시 ObjectURL 정리.
- 대용량 ZIP 메모리 경고 유지.

0.17.12 기준:
- autoZipMaxBytes 약 192MiB.
- zipWarnBytes 약 256MiB.

새 upstream이 더 좋은 streaming ZIP을 제공하면 upstream 방식을 유지해도 된다.
중요한 건 “다중 다운로드 누락 방지” 계약이다.

[C7. JSON Repair]
대상:
- 전체 재구축 결과 import.
- 통합 이어갱신 결과 import.

규칙:
- source 전체 reread 전에 cheap local parse/schema 검사를 먼저 할 수 있음.
- JSON syntax / local schema / 필수 필드 / enum 등 “수정 가능한 로컬 오류”만 repair UI 허용.
- source hash / room / branch / job / guide hash / revision / stale / 저장본 불일치는 repair 대상이 아님.
- repair가 무결성 검증 우회로가 되어서는 안 됨.
- 수정 후 기존 upstream의 parse → prepare → Diff → commit 경로를 다시 사용.
- 인앱 편집 상한 2,000,000자.

[C8. Hold / Resume]
- 다른 작업 때문에 import를 지금 시작할 수 없을 때 pasted JSON을 즉시 버리지 않음.
- 창 메모리에 보관.
- 재개 전 room / route epoch / job identity guard 확인.
- guard가 달라졌으면 재개 금지.

[C11. 응답교정 RefinerEnhanced 계약]
목표:
기존 Manager 응답교정의 판정 근거·서버 원문 검증·bridge 저장 검증을 유지하면서, 사용자가 제안을 검토/선택/직접수정하는 과정과 Crack 네이티브 수정창 경합을 안전하게 만든다.

반드시 보존할 기존 Manager refiner 기능:
- verdict/category/severity/evidence 구조와 기존 판정 의미.
- 좌우 before/after 비교 및 diff 강조.
- assertReviewSource 또는 동등한 서버 source fingerprint stale 검증.
- RP Manager AI bridge의 reviewed-response write와 저장 후 read-back 검증.
- source mutation 이후 관련 기억작업 stale 전파.
- MEMORY_STALE 보고/처리, correction archive, 처리기록, 기존 auto-apply 안전판정.

추가 계약:
1. 전체 응답 강조 미리보기
   - 선택된 교정이 적용된 전체 응답을 문맥 그대로 표시.
   - from→to 내부 최소 변경부만 강조.
   - 삭제는 〔삭제〕 또는 동등하게 명확한 시각표시.
   - 기존 좌우 비교를 대체하지 않고 보완한다.

2. 미리보기 scroll anchor
   - issue 체크/해제 전 현재 보이는 문장 주변을 anchor로 저장.
   - rerender 뒤 동일 문장을 찾아 가능한 한 같은 viewport 위치로 복원.
   - 못 찾으면 scroll ratio fallback.

3. 직접수정 상태 분리
   - “AI 제안 선택 모드”와 “사용자 직접수정 모드”를 명시적으로 분리.
   - 직접수정 모드에서는 issue 체크박스/전체선택 잠금.
   - selection rerender가 직접 편집 textarea를 덮어쓰면 불합격.
   - 편집 취소 후에만 선택모드로 복귀.

4. logical issue atomicity
   - 기본 출력은 issues[].replacements[] 구조를 우선.
   - 한 logical issue의 복수 replacement는 체크박스 하나로 함께 선택/적용.
   - 서로 다른 issue는 독립 선택 가능.
   - 동일 원본 기준 replacement range가 겹치면 적용 전에 거부.
   - legacy top-level replacements[] 입력은 후방호환 가능.

5. auto-apply atomicity
   - 한 issue의 모든 replacement가 자동반영 조건을 만족할 때만 issue 전체 자동반영.
   - 일부만 조건을 만족하면 해당 issue 전체를 확인 팝업으로 보낸다.
   - partial auto-apply 뒤 남은 issue metadata/index를 0..N-1로 재정렬하거나 동등한 안정 구조를 사용.

6. Crack native edit guard
   - 네이티브 메시지 수정창이 열려 있으면 교정 적용/표시 직전에 닫힘을 기다린다.
   - 같은 message ID인데 본문이 달라지면 사용자가 직접 수정한 것으로 보고 기존 교정 제안 폐기.
   - 완전히 새로운 최신 AI 응답이면 stale 결과를 적용하지 않고 최신 응답 재검수.
   - 기존 서버 fingerprint stale 검증을 제거하지 않는다. UI guard + 서버 guard를 함께 사용한다.

새 upstream이 이미 더 강한 diff/atomic editor/state machine을 갖고 있으면 그 구현을 유지하고 위 계약만 만족시키면 된다.
별도 응답교정 ONLY 스크립트 전체 UI/API/provider 코드를 복붙하지 않는다.
